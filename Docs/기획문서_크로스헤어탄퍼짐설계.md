# 크로스헤어 & 탄퍼짐/반동 설계 (통상 · 견착 기준)

> [기획문서_무기전투조작설계.md](./기획문서_무기전투조작설계.md) 4장의 조준 상태 머신(Relaxed/Shouldered/Aiming)을 전제로, **Relaxed(통상, 힙파이어) / Shouldered(견착)** 두 상태에서의 크로스헤어 표시와 반동(Recoil)에 의한 탄퍼짐(Spread) 모델을 설계한다.
> `Aiming`(정조준)은 조준경/아이언사이트를 통해 직접 보는 상태이므로 화면 크로스헤어 UI 자체가 존재하지 않는다 — 이번 문서의 범위 밖이며, 9장에서 후속 범위로만 짚는다.
> 작성일: 2026-09-17

---

## 1. 설계 원칙

1. **크로스헤어는 Relaxed·Shouldered 전용 HUD 요소**다. `Aiming` 진입 시 크로스헤어는 페이드아웃되어 사라지고, 대신 무기 자체의 조준경 그래픽(스코프 레티클) 또는 아이언사이트 3D 모델이 화면 중앙을 대신한다.
2. **크로스헤어는 무기별로 커스터마이즈 가능**해야 한다(모양, 굵기, 길이, 최소/최대 간격, 색상 등을 무기 데이터에서 정의).
3. **크로스헤어의 벌어짐(간격)은 실제 탄퍼짐(Spread) 각도를 화면에 투영한 결과**여야 한다 — 즉 크로스헤어는 장식이 아니라 "지금 쏘면 탄이 흩어질 범위"를 정직하게 보여주는 게임플레이 정보다.
4. **반동(Recoil)과 탄퍼짐(Spread)은 별개의 시스템**으로 분리한다.
   - **Recoil**: 발사 시 조준 방향(카메라) 자체가 강제로 밀리는 값 — 플레이어가 마우스로 되받아쳐서 상쇄(제어)할 수 있음.
   - **Spread**: 조준 중심 주변에 탄이 무작위로 흩어지는 원뿔(콘) 범위 — 플레이어가 직접 상쇄할 수 없고, 정지/웅크림/견착 등 자세로만 줄일 수 있음.
   - 최종 탄 방향 = (카메라 방향 + Recoil 오프셋) 기준으로 Spread 콘 내부에서 무작위 샘플링.

## 2. 크로스헤어 표시 규칙

| 상태 | 크로스헤어 | 기준 |
|---|---|---|
| **Relaxed**(통상/힙파이어) | 표시 (기본 크기) | `baseSpreadHipfire` |
| **Shouldered**(견착) | 표시 (더 타이트) | `baseSpreadShoulder` (Hipfire 대비 약 60%) |
| **Aiming**(정조준) | **숨김** | 조준경/아이언사이트가 대체, 5.5절 참고 |

- 상태 전이 시 크로스헤어 크기·투명도는 즉시 스냅이 아니라 **약 0.1초 보간**으로 자연스럽게 변한다(다른 문서들의 "즉시 스냅 금지, 짧게 보간" 원칙과 통일).
- `Shouldered`↔`Relaxed`는 [무기전투조작설계](./기획문서_무기전투조작설계.md)의 RMB 홀드/릴리즈에 연동되어 자동으로 전환된다.

## 3. 무기별 크로스헤어 커스터마이즈

### 3.1 데이터 구조 (개념)

```
CrosshairProfile (WeaponData에 포함되는 필드 그룹)
├─ shapeType: enum { Cross, CrossWithDot, Dot, Circle, Chevron, Hidden }
├─ barCount: int              // Cross 형태일 때 라인 수 (기본 4, 샷건류는 굵고 짧게)
├─ barThickness: float
├─ barLength: float
├─ centerDotEnabled: bool
├─ color / opacity
└─ dynamicScale: bool         // false면 Spread와 무관하게 항상 고정 크기(특수 연출용)
```

- `shapeType = Hidden`으로 두면 해당 무기는 힙파이어/견착에서도 크로스헤어를 표시하지 않는 특수 설계(예: 완전 근접 전용 무기)가 가능하다.
- 무기 타입별 기본 프리셋 예시: 돌격소총(Cross+Dot, 중간 굵기), 샷건(넓은 Circle, Spread에 매우 민감하게 반응), 권총(가는 Cross), 저격소총(Relaxed/Shouldered에서는 매우 넓은 Cross — "이 무기는 힙파이어로 맞히기 어렵다"는 것을 시각적으로 강하게 전달).

### 3.2 화면 투영 방식

- 크로스헤어 각 라인의 픽셀 간격(gap)은 **현재 Spread 각도 → 카메라 FOV/해상도 기준으로 화면에 투영한 값**으로 계산한다(고정 픽셀 값이 아님). 이렇게 해야 FOV 옵션을 바꾸거나 해상도가 달라져도 "크로스헤어가 실제 탄퍼짐과 항상 일치"하는 정직성이 유지된다.
- 개념식: `gapPixels = tan(spreadAngleRadians) * projectionDistance * screenScaleFactor` (정확한 상수는 구현 단계에서 카메라 투영 행렬 기준으로 보정).

## 4. 탄퍼짐(Spread) 모델

### 4.1 파라미터 (무기 데이터)

| 파라미터 | 설명 | 예시값 (돌격소총 기준) |
|---|---|---|
| `baseSpreadHipfire` | Relaxed 정지 상태의 기본 확산 각도 | 3.0° |
| `baseSpreadShoulder` | Shouldered 정지 상태의 기본 확산 각도 | 1.8° (Hipfire × 0.6) |
| `spreadPerShot` | 발사 1회당 누적 확산 증가량 | +0.3° |
| `maxSpread` | 연사 시 도달 가능한 확산 상한 | 8.0° |
| `spreadRecoveryDelay` | 마지막 발사 후 회복이 시작되기까지 대기 시간 | 0.15초 |
| `spreadRecoveryRate` | 초당 확산 감소량(회복 속도) | 4.0°/s |
| `movementSpreadBonus` | 이동 중 가산되는 확산 (걷기 기준) | +1.0° |
| `sprintSpreadBonus` | 스프린트 중 추가 가산 | +2.0° (이동 보너스에 추가 합산) |
| `crouchSpreadReduction` | 웅크리기 중 감산 | −0.8° |
| `airborneSpread` | 공중(점프/낙하) 상태일 때의 고정 확산(가산이 아니라 즉시 상한 근접치로 설정) | `maxSpread`의 80% |

### 4.2 계산 로직 (의사코드)

```csharp
float GetCurrentSpread(WeaponData w, PlayerState s)
{
    float baseSpread = s.stance == Stance.Shouldered ? w.baseSpreadShoulder : w.baseSpreadHipfire;

    if (s.isAirborne)
        return Mathf.Max(baseSpread, w.maxSpread * 0.8f); // 공중에서는 자세와 무관하게 크게 벌어짐

    float stanceBonus = 0f;
    if (s.isSprinting)      stanceBonus += w.sprintSpreadBonus;
    else if (s.isMoving)    stanceBonus += w.movementSpreadBonus;
    if (s.isCrouching)      stanceBonus -= w.crouchSpreadReduction;

    float total = baseSpread + stanceBonus + accumulatedFireSpread; // 4.3의 발사 누적값
    total *= s.debuffSpreadMultiplier; // 뇌진탕/탈진 등 생리 상태형 디버프 배율, 기본값 1.0
    return Mathf.Clamp(total, baseSpread, w.maxSpread);
}
```

> **연동**: `debuffSpreadMultiplier`는 [기획문서_피해디버프시스템설계.md](./기획문서_피해디버프시스템설계.md) 5.1/5.3절의 뇌진탕·탈진 디버프가 곱해 넣는 배율이다(예: 뇌진탕 2단계 +35% → 1.35). 디버프가 없으면 1.0으로 기존 계산과 동일하게 동작한다.

### 4.3 발사에 의한 누적과 회복

```csharp
// 발사 시
accumulatedFireSpread = Mathf.Min(accumulatedFireSpread + w.spreadPerShot, w.maxSpread);
timeSinceLastShot = 0f;

// 매 프레임
timeSinceLastShot += Time.deltaTime;
if (timeSinceLastShot >= w.spreadRecoveryDelay)
    accumulatedFireSpread = Mathf.Max(0f, accumulatedFireSpread - w.spreadRecoveryRate * Time.deltaTime);
```

- **결정 사항**: 회복은 즉시 시작하지 않고 `spreadRecoveryDelay`(약 0.15초)만큼 대기 후 시작한다 — 발사를 멈춘 직후 바로 정확해지면 "연사 직후 즉시 정밀 사격"이 가능해져 연사 모드의 페널티가 무의미해지기 때문.
- 샷건류는 `spreadPerShot`을 거의 0으로 두되(펠릿 수 자체가 흩어지는 무기라 탄창 하나로 퍼짐을 이미 표현) `baseSpreadHipfire` 자체를 크게 잡는 방향을 권장.

## 5. 반동(Recoil) 모델

### 5.1 파라미터 (무기 데이터)

| 파라미터 | 설명 |
|---|---|
| `recoilKickVertical` | 발사 1회당 카메라 Pitch(상방) 가산 각도 |
| `recoilKickHorizontalPattern` | 좌우 반동 패턴 — 5.2절 참고 |
| `recoilRecoverySpeed` | 초당 카메라가 원래 조준 방향으로 복귀하는 속도 |
| `recoilPerShotDecayOnAuto` | 연사 지속 시 반동이 점점 커지는 정도(초반 탄이 약하고 후반 탄이 강해지는 커브, 선택적) |

### 5.2 패턴 방식 — 고정 패턴 + 지터 혼합

- **결정 사항**: 완전 랜덤 반동이 아니라, 무기별로 **사전 정의된 반동 시퀀스(패턴)** 를 기본으로 하고 여기에 소폭의 랜덤 지터(±10~15%)를 더하는 방식을 채택한다.
  - 이유: 완전 랜덤이면 실력으로 반동을 "학습해서 제어"하는 재미가 사라지고, 완전 고정이면 매크로성 보정이 너무 쉬워져 긴장감이 없다. 패턴 + 지터 혼합이 두 장점을 절충한다(다수의 밀리터리 슈팅 게임에서 검증된 방식).
- 패턴은 연사 진행 tick 인덱스(1발째, 2발째, …)에 대응하는 `(pitchDelta, yawDelta)` 배열로 무기 데이터에 저장한다. 시퀀스를 넘어가면 마지막 값 반복 또는 순환.

### 5.3 반동 적용과 회복

```csharp
// 발사 시 (연사 n번째 탄)
Vector2 kick = weapon.recoilPattern[Mathf.Min(shotIndex, pattern.Length - 1)];
kick += RandomJitter(kick, jitterRatio: 0.12f);
recoilOffset += kick; // 카메라 회전에 누적 가산되는 오프셋

// 매 프레임: 오프셋을 서서히 0으로 되돌림 (발사를 멈추면 서서히 원위치)
recoilOffset = Vector2.MoveTowards(recoilOffset, Vector2.zero, recoilRecoverySpeed * Time.deltaTime);

// 최종 카메라 회전 = 플레이어 Look 입력 기준 회전 + recoilOffset
```

- **플레이어가 마우스를 반동 반대 방향(아래)으로 내리면**, `Look` 입력이 실제 카메라 회전 목표치를 직접 바꾸므로 `recoilOffset`이 자연스럽게 상쇄되는 체감을 준다 — 별도의 "반동 제어 입력"을 새로 만들 필요 없이 기존 `Look` 액션만으로 자연스럽게 구현된다.

### 5.4 Spread와 Recoil의 자세(Stance)별 배율

| 상태 | Spread(탄퍼짐) | Recoil(반동) 크기 |
|---|---|---|
| Relaxed(통상) | 100% (기준) | 100% |
| Shouldered(견착) | 약 60% | 약 80% (몸을 고정해 살짝 완화) |
| Aiming(정조준) | 약 10~15% (거의 고정, 5.5절 참고) | 100%지만 FOV가 좁아 화면상 체감 반동은 더 크게 느껴짐(카메라 흔들림/스코프 sway로 별도 표현) |

### 5.5 Aiming(정조준) 중 처리 — 이번 문서 범위 밖, 방향성만 명시

- `Aiming` 중에는 크로스헤어 UI가 없으므로 Spread/Recoil을 화면에 **직접 시각화하지 않는다**. 대신:
  - Spread는 매우 작은 값으로 유지되어 사실상 "조준한 곳에 거의 정확히 맞는다"는 체감을 준다.
  - Recoil은 카메라/스코프 자체의 흔들림(스코프 sway, 화면 kick)으로 체감되며, 별도 문서([무기전투조작설계](./기획문서_무기전투조작설계.md) 4장 확장)에서 스코프 레티클 흔들림 연출을 다룰 것을 9장 후속 범위로 남긴다.

## 7. 결정 사항 요약

- 크로스헤어는 **Relaxed·Shouldered 전용**, `Aiming` 진입 시 페이드아웃되어 사라지고 조준경/아이언사이트로 대체(0.1초 보간 전환).
- 크로스헤어 간격은 **실제 Spread 각도를 화면에 투영한 값**으로 계산 — 장식이 아니라 정직한 게임플레이 정보로 취급.
- **Spread(탄퍼짐)**: 발사당 누적, 마지막 발사 후 `spreadRecoveryDelay`(0.15초) 대기 후 회복 시작. 이동/스프린트/공중은 가산, 웅크리기는 감산, Shouldered는 Hipfire 대비 약 60%.
- **Recoil(반동)**: Spread와 완전히 분리된 시스템. **고정 패턴 + 소폭 랜덤 지터(±12%)** 방식 채택(완전 랜덤도, 완전 고정도 아님). 플레이어의 `Look` 입력만으로 자연스럽게 상쇄 가능하도록 카메라 회전에 누적 오프셋 형태로 적용.
- 자세별 배율: Relaxed 100%/100%(Spread/Recoil), Shouldered 60%/80%, Aiming 10~15%/100%(단, Aiming의 Recoil은 크로스헤어가 아니라 스코프 sway로 체감).
- 무기별 커스터마이즈: `CrosshairProfile`(모양/굵기/길이/색상) + Spread/Recoil 수치 파라미터를 무기 데이터(`WeaponData`)에 함께 저장.

## 8. 추가 권장 사항

- **히트마커 연동**: 크로스헤어 중심에 피격 확인 마커(X자 등)를 짧게 표시하는 기능을 크로스헤어 시스템과 같은 렌더 컴포넌트에서 함께 관리할 것을 권장(관리 포인트 단일화).
- **디버그 시각화 연계**: [캐릭터조작설계](./기획문서_캐릭터조작설계.md) 8장의 `ToggleVisionGizmo`(F3) 디버그 키에 "현재 Spread 콘을 3D로 그려서 보여주는" 옵션을 추가하면, 밸런싱 중 실제 탄퍼짐 범위를 직관적으로 검증할 수 있다.
- **접근성 옵션**: 크로스헤어 색상(색맹 모드 대비), 항상 고정 크기로 표시(Spread 반영 Off) 옵션을 설정 메뉴에 제공할 것을 권장 — 일부 플레이어는 동적 크로스헤어보다 정적 크로스헤어를 선호.
- **탄퍼짐 디자인 문서와 무기 밸런싱 시트 분리**: 본 문서의 6장 수치는 예시일 뿐이며, 실제 수치는 별도 스프레드시트로 관리하고 이 문서는 "공식/규칙"만 유지하는 것을 권장(수치가 자주 바뀌어도 설계 문서가 낡지 않도록).

## 9. 후속 설계 범위

- `Aiming`(정조준) 중 스코프 sway/레티클 흔들림 연출 세부 설계 (5.5절에서 방향성만 제시).
- UI 조작(UI 맵) 세부 바인딩 — 다음 문서에서 설계.
- 히트마커/피격 피드백 UI 세부 설계.
- 무기별 실제 수치 밸런싱 (본 문서 6장은 예시치).
- **[검토 필요] 1인칭/3인칭 시점별 정확도 차등 미반영**: [메인 기획서](./기획문서_시점전환슈팅게임.md) 2.1절·4.1절은 "1인칭이 3인칭보다 반동/탄퍼짐 페널티가 적다"는 것을 핵심 컨셉이자 `WeaponData.fpAccuracyMultiplier`/`tpAccuracyMultiplier`로 명시했으나, 본 문서의 `GetCurrentSpread`(4.2절)와 파라미터 표(4.1절)에는 시점(1인칭/3인칭) 관련 항이 전혀 없다 — 현재 설계대로면 Relaxed/Shouldered 상태의 탄퍼짐이 시점과 무관하게 동일하게 계산된다. `total *= s.viewModeSpreadMultiplier` 같은 항을 추가해 메인 기획서의 의도를 실제로 반영할지, 아니면 시점별 차이는 FOV/화면 정보량만으로 충분하다고 보고 메인 기획서 쪽을 수정할지 후속 결정 필요.
