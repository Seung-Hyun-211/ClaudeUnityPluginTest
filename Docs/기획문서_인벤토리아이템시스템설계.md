# 인벤토리 · 아이템 시스템 설계 (무게 · 컨테이너 · 중첩 보관)

> [기획문서_상점시스템설계.md](./기획문서_상점시스템설계.md) 11장에서 "인벤토리 시스템 본체(아이템 데이터, 보유/장착 로직, 인벤토리 UI)"로 범위 밖에 남겨두었던 후속 문서. 상점의 판매/교환 탭, 향후 장비/전투 시스템이 여기에 의존한다.
> 드래그 앤 드롭 등 조작 입력은 새 Action Map을 만들지 않고 [기획문서_UI조작설계.md](./기획문서_UI조작설계.md) 9장에서 이미 권장한 `Click`(press/hold/release)+`Point` 조합을 그대로 재사용한다.
> 작성일: 2026-09-18

---

## 1. 설계 원칙

1. **모든 아이템은 무게(weight)를 가진다.** 캐릭터가 휴대할 수 있는 총 무게는 고정값이 아니라 **힘(Strength) 스탯에 비례한 상한**을 가진다.
2. **리그(Rig)·가방(Bag)도 하나의 아이템이다.** 인벤토리 슬롯을 차지하는 크기(size)를 가지는 동시에, 자기 자신만의 내부 보관 공간(슬롯)을 제공하는 **컨테이너 아이템**으로 취급한다.
3. **컨테이너는 중첩 가능**하다 — 가방 속에 리그를 넣고, 리그 속에 소모품을 넣는 식으로 슬롯을 최대한 활용할 수 있어야 한다.
4. **새로운 입력 액션을 추가하지 않는다.** 더블클릭·드래그 모두 기존 `UI` 맵의 `Click`/`Point`만으로 구현한다(6장).

---

## 2. 무게 & 휴대 한계

### 2.1 데이터

```
ItemData
├─ itemId
├─ weight: float          // 개당 무게
└─ ...(기존 필드)

CharacterStats
├─ strength: int
└─ carryCapacity: float   // = f(strength), 예: base + strength * weightPerStrength
```

- **결정 사항**: `carryCapacity`는 매 프레임 재계산하지 않고, `strength`가 변할 때(레벨업, 버프/디버프, 부적 장착 등)만 갱신되는 캐시 값으로 둔다 — 인벤토리를 열 때마다 스탯을 다시 조회하는 비용을 피한다.
- 현재 휴대 무게(`currentWeight`)는 인벤토리에 담긴 모든 아이템(컨테이너 내부 아이템 포함)의 무게 합.

### 2.2 초과 시 처리

- **결정 사항**: 무게 초과는 "획득 자체를 막지" 않는다 — 대신 `currentWeight > carryCapacity`인 동안 **이동 속도 페널티**([기획문서_피해디버프시스템설계.md](./기획문서_피해디버프시스템설계.md)의 디버프 프레임워크 재사용 가능)를 적용한다. 루팅 기반 전투 루프에서 "가득 차면 아예 못 줍는다"는 마찰보다, "과적재하면 느려진다"는 트레이드오프가 재미를 더 준다고 판단.
- 인벤토리 UI 상단에 `현재무게 / 최대무게` 게이지를 상시 표시하고, 초과 시 게이지를 경고색으로 표시.

## 3. 컨테이너 아이템 (리그 · 가방)

```
ContainerItemData : ItemData
├─ containerSize: { width, height }   // 인벤토리 그리드 상에서 차지하는 칸 크기
├─ gridSize: { width, height }        // 내부 보관 공간 크기 (컨테이너 자신의 인벤토리)
└─ equipSlot: enum { None, Rig, Bag } // 장착 가능 부위 (미장착 시 None 취급 아님, 별도의 장착 상태 플래그로 관리)
```

- 인벤토리는 슬롯 단위가 아니라 **그리드(가로×세로) 기반**으로 설계한다 — 아이템마다 차지하는 칸 크기가 달라야 "가방 속 가방"의 공간 활용이 의미를 가진다(1×1 슬롯만 있다면 중첩 보관 자체가 무게/개수 관리와 다를 바 없어짐).
- 장착된 리그/가방의 `gridSize`는 **플레이어 본체 인벤토리 그리드에 합산**되어, 장착 즉시 가용 칸이 늘어난다. 미장착 상태(가방 속에 들어있거나 바닥에 놓인 상태)의 컨테이너는 자신의 내부 그리드를 독립적으로만 접근 가능(4장).
- 중첩 깊이는 **무제한으로 허용하되 UI/성능상 실질 제한은 3~4단계 정도로 자연히 수렴**할 것으로 예상(가방 속 가방 속 가방은 총 칸 수 대비 비효율적이라 플레이어가 스스로 안 함) — 별도의 강제 깊이 제한 로직은 넣지 않는다.

## 4. 중첩 보관 UI 흐름

```
[ 인벤토리 창 (본체 그리드) ]
 ┌───────────────────────────────┐
 │ [무기] [탄약] [ 가방 ]  ...     │   ← 미장착 "가방" 아이템을 더블클릭
 └───────────────────────────────┘
                 │ 더블클릭
                 ▼
        ┌─────────────────────┐
        │  가방 내부 (팝업 창)   │
        │  [ 리그 ] [물약] [ ]  │  ← 팝업 안의 칸도 동일하게 상호작용 가능
        │  [  천  ] [  ] [  ]  │
        └─────────────────────┘
                 │ 팝업 안의 "리그"를 더블클릭
                 ▼
        ┌─────────────────────┐
        │  리그 내부 (팝업 창)   │
        │  [탄창][탄창][  ]     │
        └─────────────────────┘
```

- **더블클릭 대상**: 인벤토리(또는 상위 팝업) 상의 **미장착** 컨테이너 아이템만 더블클릭 가능 — 장착 중인 가방/리그는 캐릭터 장착 슬롯 쪽 UI에서 이미 상시 펼쳐져 있으므로 별도 팝업이 필요 없다(중복 UI 방지).
- 팝업은 **모달이 아니라 보조 창**으로 띄운다 — 부모 인벤토리 창과 팝업 창을 동시에 보면서 서로 다른 칸끼리 드래그로 아이템을 옮길 수 있어야 하기 때문(6장 드래그 규칙과 직결).
- 팝업은 몇 개든 동시에 열 수 있다(가방 팝업 + 그 안의 리그 팝업을 나란히). 같은 컨테이너를 더블클릭하면 새 팝업을 또 열지 않고 기존 팝업에 포커스만 준다.
- 팝업 닫기: `Cancel`(Esc) 또는 팝업 우상단 닫기 버튼 — 내용물은 그대로 유지된 채 닫히기만 한다(닫아도 아이템이 튕겨 나오지 않음).

## 5. 드래그 앤 드롭 & 자동 배치

- 아이템(또는 컨테이너)을 **다른 컨테이너의 칸으로 드래그**하면, 정확히 그 칸에 맞춰 놓지 않아도 대상 컨테이너 그리드 내의 **빈 공간을 자동 탐색해 배치**한다.
  - 탐색 순서: 대상 그리드를 좌상단부터 행 우선으로 순회하며, 드래그한 아이템의 `containerSize`가 들어갈 수 있는 첫 번째 빈 영역에 배치.
  - 드롭 지점이 특정 칸 위였다면 그 칸을 우선 시도하고, 회전 없이 들어가지 않으면 위 자동 탐색으로 폴백.
  - 빈 공간이 전혀 없으면 배치를 취소하고 아이템은 원래 위치로 되돌아간다(드롭 실패 시 별도 경고 팝업 없이 조용히 복귀 — 상점 시스템의 "실수 방지는 조용히 막는다" 컨벤션과 통일).
- 드래그 대상이 **컨테이너 아이템 자체**(가방을 다른 가방 안으로 옮기는 경우)일 때도 동일 규칙을 적용하되, **자기 자신 또는 자신의 하위 컨테이너 안으로는 드롭할 수 없다**(순환 참조 방지 — 예: 가방 A 안에 가방 A를 넣거나, A 안의 리그 B 안에 A를 넣는 시도는 무효 처리).
- 이 모든 상호작용은 [UI조작설계](./기획문서_UI조작설계.md) 9장의 `Click`(press: 드래그 시작 / hold: 이동 중 / release: 드롭) + `Point`(커서 위치) 조합만으로 구현하며, 부모 창과 팝업 창 사이의 드래그도 동일한 `Point` 좌표계(스크린 좌표 → 각 창의 로컬 그리드 좌표 변환)로 처리한다.

## 6. 입력 처리 요약

| 액션 | 동작 |
|---|---|
| `Click`(더블클릭 판정) | 미장착 컨테이너 아이템 위에서 짧은 간격 2회 클릭 → 해당 컨테이너의 내부 보관 팝업 오픈 |
| `Click`(press-hold-release) + `Point` | 아이템 드래그 시작 → 이동 → 드롭 (본체 창 ↔ 팝업 창 ↔ 다른 팝업 창 모두 동일) |
| `RightClick` | 아이템 컨텍스트 메뉴(장착/버리기/정보 등, 세부는 후속 문서) |
| `Cancel` | 포커스된 팝업 창 닫기(닫아도 내용물 유지) |

- 신규 액션 없음 — 모두 [UI조작설계](./기획문서_UI조작설계.md)에 이미 정의되어 있음.

---

## 7. 결정 사항 요약

- 아이템은 **무게**를 가지며, 캐릭터의 최대 휴대 무게는 **힘(Strength) 스탯에 비례**해 산출한다(캐시 값, 스탯 변경 시에만 재계산).
- 무게 초과 시 획득을 막지 않고 **이동 속도 디버프**로 페널티를 준다.
- 리그/가방은 **크기(containerSize)를 가진 아이템**인 동시에 **자체 내부 그리드(gridSize)를 갖는 컨테이너**이며, 장착 시 본체 인벤토리 그리드에 칸이 합산된다.
- 컨테이너는 **중첩 보관 가능**(가방 속 리그, 리그 속 아이템 등), 강제 깊이 제한 없음.
- 인벤토리 창에서 **미장착 컨테이너를 더블클릭하면 보조(비모달) 팝업**으로 내부를 열 수 있고, 여러 팝업을 동시에 띄워 서로 드래그로 아이템을 옮길 수 있다.
- 아이템을 컨테이너로 드래그하면 **정확한 칸이 아니어도 빈 공간에 자동 배치**되며, 자기 자신/하위 컨테이너로의 순환 배치는 금지한다.
- 드래그 앤 드롭·더블클릭 모두 **새 입력 액션 없이** 기존 `Click`+`Point`로 구현.

## 8. 후속 설계 범위

- `ItemData`/`ContainerItemData`의 전체 필드, 아이템 등급/희귀도, 스택 가능 여부(탄약 등 동일 아이템 묶음 처리).
- 장착 슬롯 체계(무기, 방어구, 가방, 리그 각각의 장착 위치와 상호 배타 규칙).
- 아이템 획득/드랍(필드 루팅, 처치 드랍, 상자 등) — [기획문서_상점시스템설계.md](./기획문서_상점시스템설계.md) 5장(판매)이 조회할 인벤토리 API의 실제 구현.
- 컨텍스트 메뉴(`RightClick`) 세부 항목(장착, 버리기, 분할, 정보 보기). **결정(2026-09-19): "버리기"는 아이템을 월드에 떨어뜨리는 동작이다**(파괴 아님) — [world-item-factory.md](../documents/world-item-factory.md).
- 그리드 회전(아이템을 90도 돌려서 배치) 지원 여부 — 우선 미지원으로 시작하고 필요 시 추가.
